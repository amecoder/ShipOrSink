## 진척 없는 3회 회로차단기 + 에러 분류

**업계 표준: 같은 실패가 진척 없이 3회 반복되면 재시도를 멈춘다.** 재시도 자체보다 "이 실패가 재시도로 해결 가능한 종류인가"를 먼저 분류하는 것이 핵심이다 — 무의미한 재시도는 컨텍스트만 오염시킨다.

### 에러 분류 → 대응 전략 매핑

| 분류 | 특징 | 예시 | 대응 전략 |
|------|------|------|----------|
| **일시적 오류** (재시도 유효) | 환경·타이밍 의존, 같은 입력이라도 결과가 달라짐 | 네트워크 타임아웃, 포트 충돌, flaky 테스트, 레이스 컨디션, 외부 API rate limit | 즉시 1회 재시도 → 그래도 실패하면 원인을 "일시적"에서 "구조적"으로 재분류 |
| **구조적 오류** (재시도 무의미) | 같은 입력·같은 코드면 항상 같은 실패 | 타입 에러, 로직 버그, 누락된 의존성, 잘못된 API 시그니처, 컴파일 에러 | 재시도 금지 — [체계적 디버깅 프로세스](#체계적-디버깅-프로세스-phase-2-3에서-참조)로 근본원인 조사 |
| **요청 자체 오류** (재시도 무의미, 재구성 필요) | 요구사항·스펙이 모순되거나 실현 불가능 | SPEC의 Invariant와 AC가 충돌, 존재하지 않는 API를 요구, 아키텍처적으로 불가능한 제약 | 재시도·디버깅 모두 무의미 — 사용자에게 에스컬레이션 (Phase 0/1 문서 자체를 재협의) |
| **리뷰 의견 충돌** (재시도 무의미) | Claude와 Codex(또는 두 리뷰어)가 상충하는 지적 | 한쪽은 "이 패턴이 버그"라 하고 다른 쪽은 "의도된 동작"이라 함 | 자동 재시도 금지 → 번호 붙인 평문 질문으로 양쪽 근거를 제시하고 사용자 판단 |

**분류 절차**:
1. 실패가 처음 발생하면 위 표에서 분류를 가정한다 (기본값: 구조적 오류로 취급 — 안전 측)
2. 같은 수정으로 2회 연속 실패하면 분류를 재검토한다: 매번 다른 지점에서 실패하는가? → 일시적 오류였을 가능성
3. **같은 실패가 진척 없이 3회** 이어지면 분류와 무관하게 **회로차단기 발동** — 더 이상 자동 재시도하지 않고 BLOCKED로 전환, `debug-specialist` 위임 또는 사용자에게 보고. 실패 집합이 줄어드는 동안은 다른 실패를 고치는 것이라 세지 않고, 전체 반복 상한 10 이 폭주를 막는다 — 판정 규칙: [done-loop.md 멈춤 조건](done-loop.md#루프와-멈춤-조건)

### 재시도 카운터 관리

- `retry_count`는 STATE.md에 단계별로 기록한다 (Phase 2 각 Step). 구현 뒤 검증 루프는 `done.loop_iter`·`done.stall` 과 Done Loop 표로 기록한다 ([done-loop.md](done-loop.md#루프와-멈춤-조건))
- 재시도 사이 **다른 가설**을 적용해야 카운트가 유효하다 — 같은 수정을 반복하는 것은 재시도가 아니라 방치다
- BLOCKED 시: 실패한 단계, 시도한 수정 목록과 각 결과, 아키텍처 의심 사항을 STATE.md에 기록하고 사용자에게 보고. `--resume`으로 재개 가능

## 회귀 규칙 요약 (tdd/full 모드)

Step 7·8 의 실패는 따로 세지 않고 하나의 완료 판정 루프(Step 7 묶음 + `done.sh`)에서 **실패 집합**으로 함께 센다. "진척 없이 3회"는 같은 항목이 연속 3회 실패하는 동안 실패 집합이 한 번도 줄지 않은 경우다(기준선 제외). done.sh 자체가 고장 나면(`DONESH`) 곧바로 멈춘다.

| 실패 지점 | 회귀 대상 | 멈춤 조건 | 멈추면 |
|----------|----------|----------|-------|
| Step 5 (GREEN) 실패 | Step 5 재시도 | 같은 테스트가 진척 없이 3회 실패 (`retry_count`) | 아키텍처 재검토 → BLOCKED |
| Step 7a (Build) 실패 → `BUILD` | Step 5 (구현 수정) | 완료 판정 루프: 진척 없이 3회 · 전체 10회 · 재시도 무의미 | BLOCKED |
| Step 7b (Typecheck) 실패 → `TYPE` | Step 5 (타입 수정) | 완료 판정 루프 (위와 같음) | BLOCKED |
| Step 7c (Lint) 실패 → `LINT` | Step 6 (리팩터 수정) | 완료 판정 루프 (위와 같음) | BLOCKED |
| Step 7d (Unit Test) 실패 → `TEST` | Step 5 | 완료 판정 루프 (위와 같음) | 아키텍처 재검토 → BLOCKED |
| Step 8 `done.sh` FAIL (AC-xx) | Step 4 (RED) | 완료 판정 루프 (위와 같음) | BLOCKED |
| Step 9 (E2E) 실패 | Step 5 또는 Step 8 | 같은 시나리오 진척 없이 3회 | BLOCKED |
| SDD Spec 리뷰 실패 | 구현 에이전트 수정 | 같은 지적이 진척 없이 3회 | 태스크 재분해 또는 BLOCKED |
| 게이트 ⓐ Major 수용분 | 해당 문서 수정 | 재리뷰 1회 | 사용자 결정으로 종결 |
| 게이트 ⓑ Major 수용분 | Step 5 (구현 수정) | 재리뷰 1회 | 사용자 결정으로 종결 |

**BLOCKED 시**: STATE.md에 다음을 기록 후 사용자에게 보고:
- 실패한 단계와 에러 메시지
- 시도한 수정 목록과 각 결과
- 아키텍처 의심 사항 (진척 없는 3회 실패 시)
- `--resume`으로 재개 가능

`quick` 모드도 같은 완료 판정 루프를 쓴다(Build→Co-Review→Test/QA→`done.sh`) — [quick-mode.md](quick-mode.md#루프-제어) 참조.

## 체계적 디버깅 프로세스 (Phase 2-3에서 참조)

어디서든 빌드/테스트 실패가 발생하면 이 프로세스를 따른다.

### Phase A: 근본원인 조사

1. **에러 메시지 완독** — 스택 트레이스, 라인 번호, 에러 코드
2. **재현 확인** — 안정적으로 트리거 가능한가?
3. **최근 변경 확인** — `git diff`, 최근 커밋, 의존성/설정 변경
4. **다중 컴포넌트 시스템이면** — 각 경계에서 입출력을 로깅하여 어디서 깨지는지 특정
5. **데이터 흐름 추적** — 잘못된 값의 원점을 거슬러 올라간다

### Phase B: 패턴 분석

1. 같은 코드베이스의 작동하는 유사 코드를 찾는다
2. 작동하는 것과 깨진 것의 차이를 나열한다
3. "그건 상관없을 거야"라고 가정하지 않는다

### Phase C: 가설 검증

1. 단일 가설: "X가 원인이다. 왜냐하면 Y"
2. 가설을 검증하는 최소 변경 1개만 적용
3. 통과하면 → 수정 확정
4. 실패하면 → 새 가설 (기존 수정 위에 덧붙이지 않는다)

### Phase D: 진척 없는 3회 실패 시 아키텍처 재검토

- 매 수정마다 다른 곳에서 새 문제가 발생하는가?
- "대규모 리팩터링"이 필요한가?
- 이 패턴을 관성으로 고수하고 있지 않은가?
→ 사용자와 논의 후 진행

## Ralph Loop

완료 판정 루프는 기본적으로 세션 안에서 돈다. 사람이 자리를 비우는 장시간 무인 실행에서만 `ralph-loop` 플러그인을 쓰고, promise 는 같은 응답에서 `done.sh` 가 exit 0 으로 끝난 직후에만 출력과 함께 낸다 — promise 문구만으로는 위조할 수 있어서다. 프롬프트와 절차: [done-loop.md](done-loop.md#무인-장시간-실행--ralph-loop)

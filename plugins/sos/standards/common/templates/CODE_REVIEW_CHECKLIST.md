# 코드 리뷰 체크리스트

> 리뷰어가 PR 리뷰 시 참고하는 체크리스트.
> 심각도: **MUST** (필수) / **SHOULD** (권장) / **COULD** (선택)
> 리뷰 우선순위: 정확성/보안 > 데이터 안전 > 운영성 > 설계 > 스타일

---

## 1. 정확성 (Correctness)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 요구사항을 정확히 충족하는가? |
| MUST | 엣지 케이스를 처리하는가? (null, 빈 값, 경계값) |
| MUST | 에러 핸들링이 적절한가? (사용자 친화적 메시지, 적절한 HTTP 코드) |
| MUST | 동시성/경합 조건이 안전하게 처리되는가? |
| SHOULD | 하위 호환성이 유지되는가? (Breaking Change 없음) |

## 2. 보안 (Security)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 하드코딩된 시크릿 없는가? (API 키, 비밀번호, 토큰) |
| MUST | 사용자 입력을 검증하는가? |
| MUST | SQL 인젝션 방지 (파라미터화 쿼리 / ORM) |
| MUST | XSS 방지 (입력 이스케이프 / 프레임워크 자동 이스케이프) |
| SHOULD | CSRF 보호가 적용되어 있는가? |
| SHOULD | 인증/인가가 올바르게 구현되어 있는가? |
| SHOULD | 에러 메시지에 민감한 정보가 노출되지 않는가? |

## 3. 데이터 안전 (Data Safety)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 데이터 손실 가능성이 없는가? (삭제, 덮어쓰기) |
| MUST | 마이그레이션이 롤백 가능한가? |
| SHOULD | 트랜잭션 경계가 올바른가? |
| SHOULD | 대량 데이터 처리 시 페이지네이션/스트리밍을 사용하는가? |

## 4. 운영성 (Operability)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 적절한 로깅이 추가되어 있는가? (에러, 주요 비즈니스 이벤트) |
| SHOULD | 장애 시 원인을 파악할 수 있는 충분한 정보가 있는가? |
| SHOULD | 메트릭/모니터링이 필요한 변경인가? (필요 시 추가) |
| SHOULD | Feature flag로 점진적 롤아웃이 가능한가? (고위험 변경) |
| COULD | 배포 후 검증 방법이 명확한가? (health check, smoke test) |

## 5. 설계 (Design)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 변경이 하나의 목적에 집중하는가? (관심사 분리) |
| MUST | 이 변경을 수정해야 할 때, 영향 범위가 적절한가? (변경 격리) |
| SHOULD | 실패했을 때 시스템이 안전한 상태로 복구되는가? (실패 모드) |
| SHOULD | 적절한 추상화 수준인가? (과도한 추상화 / 추상화 부족) |
| SHOULD | 중복 코드가 없는가? (DRY 원칙) |
| COULD | 적절한 디자인 패턴이 사용되었는가? |

## 6. 코드 품질 (Code Quality)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 네이밍이 명확하고 프로젝트 컨벤션을 따르는가? |
| MUST | 함수 길이 ≤50줄, 파일 크기 ≤800줄 (Kotlin ≤600줄) |
| MUST | 복잡도 ≤15 (McCabe / Cyclomatic) |
| MUST | 매직 넘버 없이 명명된 상수를 사용하는가? |
| SHOULD | 깊은 중첩 없는가? (≤4단계) |
| SHOULD | 불변성(immutability)을 지키는가? |
| COULD | 주석 처리된 코드, 미사용 변수/import가 없는가? |

## 7. 성능 (Performance)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | N+1 쿼리 문제가 없는가? |
| SHOULD | 불필요한 연산/호출이 없는가? |
| COULD | 적절한 캐싱 전략이 적용되어 있는가? |
| COULD | 비동기 처리가 필요한 작업에 async를 사용하는가? |

## 8. 테스트 (Testing)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 새로운 기능에 단위 테스트가 있는가? |
| MUST | 기존 테스트가 모두 통과하는가? |
| SHOULD | 테스트 커버리지 ≥80%인가? |
| SHOULD | 의미 있는 assertion을 사용하는가? (단순 `assertTrue` 지양) |
| SHOULD | 엣지 케이스 / 실패 케이스 테스트가 있는가? |
| COULD | 통합 테스트가 포함되어 있는가? |

## 9. 문서 (Documentation)

| 심각도 | 점검 항목 |
|--------|-----------|
| MUST | 모든 public 함수/클래스에 문서화(docstring/KDoc/TSDoc)가 있는가? |
| SHOULD | 복잡한 비즈니스 로직에 설명 주석이 있는가? |
| SHOULD | 아키텍처 변경 시 ADR이 작성되었는가? |
| COULD | CHANGELOG.md가 갱신되었는가? |

---

## 리뷰 코멘트 접두사

| 접두사 | 의미 | 수정 필수 |
|--------|------|-----------|
| `[BLOCKER]` | 반드시 수정해야 할 심각한 문제 | O |
| `[SUGGESTION]` | 개선 제안 (선택적) | X |
| `[QUESTION]` | 이해를 위한 질문 | X |
| `[NIT]` | 사소한 스타일/취향 | X |
| `[PRAISE]` | 잘한 부분 칭찬 | - |

## 리뷰 응답 시간

- 첫 리뷰: PR 제출 후 **4시간 이내**
- PR 크기: **400줄 이하** 권장 (초과 시 분할 요청)
- 리뷰 우선순위: 정확성/보안 > 데이터 안전 > 운영성 > 설계 > 스타일
